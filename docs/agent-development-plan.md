# Agent Runtime 开发计划

状态：执行中  
更新日期：2026-08-15

## 1. 目标与边界

插件的 Agent 不是替用户建立知识图谱，而是在一次阅读对话中完成四件事：

1. 围绕用户明确选择的原文回答问题；
2. 在得到授权时，有限地读取指定目录或联网资料；
3. 让用户看清本轮使用了哪些上下文与工具；
4. 只把用户确认的内容写入知识库。

第一版不做全库向量化、不自动写入长期知识、不自动生成复杂关系网络，也不把所有历史对话永久塞入模型。上下文是一种有限的注意力预算，而不是存储空间。

## 2. 当前基线

已有能力：

- Chat Completions / Responses API 模型调用；
- 通用工具循环、工具调用次数限制与停止信号；
- 服务商托管搜索、独立搜索和搜索故障转移；
- 指定文件夹内的两阶段本地检索；
- 选中文本、图片、连续追问、待问清单与人工摘录；
- 桌面端侧栏、独立窗口及移动端基础布局。

主要缺口：

- 上下文仍由主流程临时拼接，缺少统一预算和可检查清单；
- 模型请求、协议差异和错误判断仍混在业务流程里；
- 普通位图直接转 Base64，移动端内存风险较高；
- 临时对话仅在内存中，关闭视图或重载后丢失；
- 长对话没有稳定、可解释的压缩规则；
- 待问问题还没有形成可复用的结构化记录。

## 3. 分阶段路线

| 阶段 | 结果 | 主要交付 | 完成标准 |
|---|---|---|---|
| P0-A | 每次运行可规划、可限制 | `RunPlan`、统一字符/图片/工具预算 | 超预算内容按确定规则裁剪；工具授权冻结在本轮计划中 |
| P0-B | 上下文可解释 | `ContextBuilder`、`ContextReceipt` | 回答附带本轮各类上下文的原始量、实际量和裁剪原因 |
| P0-C | 模型接入边界清晰 | `ModelTransport`、统一错误分类 | Chat/Responses 共用一个传输入口；认证、限流、余额、超时、服务端错误可区分 |
| P0-D | 移动端图片可用 | 普通位图压缩、移动端独立图片预算 | 图片在发送前缩放压缩；移动端不会沿用桌面端 80 MB 总预算 |
| P1-A | 临时会话可恢复但不无限增长 | `SessionStore`、容量淘汰、恢复 | 重载后恢复最近会话；不保存图片二进制；超过数量或字节上限自动淘汰最旧会话 |
| P1-B | 长对话仍能稳定追问 | 一次确定性的结构化 Compaction | 超预算时保留最近原文对话，并把较早轮次压成带角色与问题线索的摘要 |
| P1-C | 问题成为可管理对象 | `QuestionRecord` | 待问、已问、已解决和暂放问题都有稳定 ID、状态、来源片段和时间 |
| P3 | 按“我的知识 / 外部材料”检索 | Scope 内正文词项缓存、身份分 lane、历史问题检索 | 外部材料不会挤掉个人内容；每段证据保留来源身份；不扫描 Scope 外文件 |
| P4 | 谨慎形成长期学习偏好 | Memory candidate、重复证据、确认/拒绝与过期机制 | Agent 只能积累候选信号，未经用户确认不进入长期上下文 |
| P5 | 可测量、可诊断、可发布 | 运行指标、容量守卫、离线评测和诊断摘要 | 性能与上下文预算可自动验证；诊断数据留在本地且有上限 |
| P6 | 大问题可控拆分 | 规划、共享父级预算、共享证据、无工具汇总 | 最多 3 个子问题；不重置工具预算；任一工具耗尽不导致整轮失败 |

## 4. P0 详细设计

### 4.1 RunPlan

每次发送时创建不可变计划，至少记录：

- 运行 ID、创建时间、桌面或移动端；
- 模型协议与联网路径；
- 被授权的本地目录；
- 总文本预算及各分区预算；
- 图片数量、单图字节、总字节与最长边；
- 工具白名单、单工具调用次数与结果长度；
- 最大工具轮数和总超时。

计划一旦进入模型调用阶段便不随设置页变化。新的设置只影响下一轮运行。

### 4.2 ContextBuilder

按以下优先级构建上下文：

1. 系统约束与本轮问题；
2. 用户选中的原文；
3. 最近几轮对话；
4. 已授权目录返回的少量证据；
5. Web 搜索返回的少量证据；
6. 更早对话的结构化压缩。

不追求填满窗口。每个分区有独立上限，总量还要受全局上限约束。被裁剪的内容必须在 Receipt 中说明。

### 4.3 Context Receipt

Receipt 是运行元数据，不进入用户知识库，包含：

- 每个上下文分区是否使用；
- 原始字符数与发送字符数；
- 是否裁剪以及裁剪原因；
- 使用的知识目录、联网路径、图片数量；
- 估算输入 Token，而不是伪装成服务商精确计费 Token。

### 4.4 ModelTransport

传输层只负责：

- 根据模型配置构造 Chat Completions 或 Responses 请求；
- 传递取消信号；
- 解析统一的 assistant message；
- 收集 Responses 来源标注；
- 把 HTTP/网络错误归一为稳定错误类型。

P0 不自动重试模型请求，避免重复计费和重复工具副作用。错误的 `retryable` 只供 UI 和后续策略判断。

### 4.5 图片预算

| 项目 | 桌面端 | 移动端 |
|---|---:|---:|
| 最多图片 | 9 | 4 |
| 单张源文件 | 10 MB | 6 MB |
| 总源文件 | 80 MB | 18 MB |
| 输出最长边 | 1600 px | 1280 px |
| JPEG/WebP 质量 | 0.82 | 0.76 |

普通 PNG/JPEG/WebP/GIF 在发送前通过 Canvas 生成受控尺寸的数据；无法安全解码的格式才在符合预算时回退原文件。

## 5. P1 详细设计

### 5.1 SessionStore

会话通过 Obsidian 官方 `Plugin.loadData()` / `saveData()` 接口存入插件 `data.json` 的独立 `localData.sections.sessions` 分区。统一的串行写入协调器保证设置、会话、学习偏好和运行诊断不会并发覆盖；各 Store 仍独立执行容量裁剪。旧版 `sessions.json` 只在升级时读取一次，成功写入新分区后删除。默认：

- 最多 20 个会话；
- 总 JSON 体积不超过 2 MB；
- 最长保留 30 天；
- 不保存 Base64、Blob、DOM 节点、运行中状态或 Secret；
- 保存图片路径和必要元数据，但不复制图片；
- 淘汰顺序为最久未更新会话优先。

这是“工作区恢复”，不是永久知识。用户确认保存的摘录仍写入其选择的 Markdown 位置。

### 5.2 一次结构化 Compaction

触发条件为会话历史超过 ContextBuilder 分配的对话预算。第一版采用确定性压缩：

- 完整保留最近若干轮；
- 早期用户问题保留为问题条目；
- 早期 AI 回答只保留有限摘要片段；
- 显式纠正和未解决问题优先保留；
- 每次构建最多生成一个压缩块，不递归压缩。

Receipt 会记录压缩前后字符数。后续只有在评测证明确定性压缩不足时，才考虑增加模型辅助摘要。

### 5.3 QuestionRecord

```ts
type QuestionRecord = {
  id: string;
  sessionId: string;
  text: string;
  status: "pending" | "asked" | "resolved" | "parked";
  sourceExcerpt: string;
  createdAt: number;
  askedAt?: number;
  resolvedAt?: number;
};
```

P1 只用于恢复、筛选和后续上下文构建；不会自动把问题写入知识笔记。

## 6. 明确不进入 P0 / P1 的内容

- 全 Vault 向量数据库；
- 自动知识图谱或“枢纽发现”；
- 后台扫描全部文件；
- 自动把 AI 回答写入 Markdown；
- 从历史对话直接更新长期学习偏好；
- 多 Agent 分工链；
- 为追求视觉效果而引入大型前端框架。

## 7. 验证与发布门槛

每个阶段至少通过：

1. TypeScript 构建和 ESLint；
2. 无网络 smoke test；
3. Chat Completions 与 Responses 请求体测试；
4. 上下文裁剪、会话淘汰、错误分类的确定性测试；
5. 桌面端和移动端布局手测；
6. 构建产物体积对比，若单阶段增长超过 15%，必须解释原因。

## 8. P3 详细设计：身份化按需检索

P3 只在用户当前授权的 Knowledge Scope 内建立运行时词项缓存，不在启动时扫描 Vault，也不引入 embedding。缓存按文件路径和 `mtime` 增量更新，并设置文件数、读取字符数和单批主线程预算。

每个检索结果必须具有保守身份：

- `personal_knowledge`：文件 frontmatter 明确声明为个人知识；
- `user_curated`：用户确认整理过，但不等同于已经掌握；
- `external_material`：网页、公众号或其他导入材料；
- `unknown`：没有足够证据，不得推断为用户知识。

排序采用分 lane 配额。Personal/User-curated 与 External/Unknown 分别保留候选，避免大量导入文章挤掉少量个人笔记。模型收到的每段正文都带身份与 epistemic status。

历史问题只检索 `QuestionRecord` 和必要来源片段，不加载旧 AI 回答全文。Context Receipt 展示实际使用的本地来源、身份、路径以及被省略数量。

P3 非目标：全 Vault 索引、向量搜索、模型推断关系、自动写双链、把保存过的 AI 回答判定为 mastered。

## 9. P4 详细设计：候选式学习记忆

学习偏好不要求用户一次性描述完整，也不能由一次对话直接确定。插件只从明确表达讲解偏好的用户消息中产生 `candidate`，并记录证据会话；同类信号必须来自多个会话才进入 `ready_for_review`。

候选状态为：

```text
candidate → ready_for_review → confirmed
                           ↘ rejected
confirmed / candidate → stale
```

只有 `confirmed` 能进入 Context，且放在小型、独立的偏好分区。候选、冲突、拒绝和过期均保留本地审计字段。用户通过管理窗口确认、拒绝或删除；模型和启发式逻辑都没有直接激活长期记忆的权限。

默认上限：50 条候选/记忆，候选 90 天未确认则 stale，确认记忆 180 天未使用会提示复核。P4 不存人格画像，不在后台遍历全部历史，也不把知识观点误当作学习方式偏好。

## 10. P5 详细设计：可观测性与发布加固

P5 记录本地、限额的运行指标：运行耗时、协议、设备、Context 估算量、图片数量、工具轮数、来源数量、完成/取消/错误类型。指标不包含原文、问题、回答、URL、路径、API Key 或工具结果。

默认只保存最近 200 次运行或 256 KB，保留 30 天。诊断摘要提供 p50/p95、错误分类、Context 裁剪率和取消率，用于决定是否真的需要语义索引、缓存或流式传输。

离线评测至少覆盖：

- 外部材料不被标记为个人知识；
- 分 lane 后个人内容不会被导入材料淹没；
- 未确认 Memory 永不进入 Context；
- 历史问题检索不携带旧回答全文；
- Scope、Session、Memory、Metrics 的容量限制；
- P0/P1 的协议、停止、图片和存储测试持续通过。

P5 不上传遥测，不自动重试有副作用的工具，不把 buffered 响应伪装成 streaming。

P3/P4/P5 完成后，再用真实使用指标决定是否立项 embedding、多级 Compaction、Prompt Cache 或跨设备 Memory 合并。路线图是可调整的计划，不是对这些复杂能力的默认承诺。

## 11. P6 详细设计：稳定工具循环与复杂问题拆分

P6 先修复基础循环，再允许复杂问题拆分：

1. 本地搜索候选上限为 6，与每次 3 段、最多 2 次读取严格匹配；
2. Tool Gateway 对规范化后的相同参数做本轮去重，缓存命中不再消耗调用预算；
3. 本地读取共享 Markdown、段落和证据字符预算，避免同一段落被重复注入；
4. 工具调用预算耗尽后返回可恢复结果并撤下该工具，模型必须使用已有材料继续回答；
5. 诊断仅记录工具名及尝试、成功、缓存命中、预算拒绝次数；
6. 自动模式只对明显包含多个独立关注点的问题调用规划器，最多产生 3 个子问题；
7. 子问题共享同一个 Tool Gateway 与证据缓存，汇总阶段不开放任何工具。

复杂问题拆分不是多 Agent 自治系统。它是单个 Controller 管理的一组受限模型调用，不允许子问题创建新权限或重置预算。服务商托管搜索暂时保持直接回答，因为插件无法观察或约束服务端内部工具循环。
