# ai-reading-companion 优化任务书（2026-09-20）

> **用途**：本文件是给本项目专属对话的执行任务书，由简历工作区会话基于 README、docs/agent-technical-design.md、docs/v1-optimization-toward-v2.md 与整体分析生成。
> **执行前先读**：README（Features 与 Agent Runtime architecture 节）、docs/agent-technical-design.md（第 656-815 行本地检索、1414-1570 行 Memory、1713-1770 行 Web Search）。
> **总病根（一句话）**：当前方案在"投入（token）"与"产出（回答质量）之间没有任何一环被测量——检索没验证过、记忆效果没对比过、context 装配质量没归因过。本任务书按"先测量、再优化"的顺序排列。

## T1【P0·先测量】建立检索 gold set，验证词法检索

**问题**：agent-technical-design 的原文承诺是"只有回归集证明存在持续同义改写漏召回，才立项 embedding"——**但这个回归集从未建立**。导致的现状：词法检索够不够用、该不该上向量、五条 lane 配额（1/3/2/2/3-4）合不合理，全部悬空。这是"检索没经过验证"的实锤。

**做法**：
1. 从真实使用中整理 20-50 个问题（可从历史会话与 docs/product-interaction-backlog.md 补充），每题标注：期望命中的笔记路径/段落（gold answer）、问题类型（概念理解/操作/对比/找原文）、是否同义改写型（问题用词与笔记原文不一致）。
2. 写一个离线评测脚本：对每题跑现有两阶段词法检索，输出命中率（gold 段落是否进 Top-N）、按问题类型分桶、同义改写子集单独统计。
3. 产出报告：整体命中率、同义改写漏召回率、各 lane 命中分布。
4. **决策规则**（预先定死，避免事后主观）：同义改写子集命中率 < 60% → 对授权 Scope 启动增量 embedding（设计已预留路径）；≥ 60% → 词法保留，只调 lane 配额。

**验收**：gold set 文件（带标注）+ 评测脚本 + 一份含决策结论的报告，存 docs/evaluation/。

## T2【P1·治 token】context 从"固定全装配"改"按需装配"

**问题**：ContextBuilder 八分区每次请求全装配（system → 选段 → 确认记忆 → 压缩块 → 本地证据 → web 证据 → 问题历史 → 尾轮），一个 10 个词的问题也背上数 K token 的上下文——这是"token 额度花得多、context 构造占 token"的机制根源。

**做法**（两方案选一，建议 A）：
- **方案 A·轻分类前置**：发送前对问题做一次廉价判断（纯规则或极短 prompt）：简单词句问题只装配 system+选段+尾轮；明确引用历史/其他笔记的问题才加本地证据与问题历史；带"之前/刚才"的问题才加压缩块与记忆。分类结果写进 Context Receipt 的分区 reason 字段（`skipped_by_policy`）。
- **方案 B·两段式**：先带最小 context 请求；模型显式调用检索/历史工具时再补装第二轮。改动更大，但更彻底。

**验收**：用 T1 的 gold set 问题集做改造前后对比——简单问题输入 token 下降 ≥60%；带上下文依赖的问题回答质量不降（人工盲评 10 题）；Receipt 仍完整可解释（跳过的分区有原因标注）。

## T3【P1·补效果数据】回答反馈按钮 + 与 Context Receipt 关联

**问题**：运行诊断面板全是运行指标（p50/p95 时延、裁剪率、失败分类），没有任何效果指标——"上下文小票"记录了用了什么，但"用了之后结果如何"没有记录，小票只有一半。质量提升不确定的问题从此无从回答。

**做法**：每条回答旁加一键反馈（有用 / 一般 / 没用，单击即存不打断）；反馈记录与本轮 Receipt 的分区使用摘要（各分区 included/truncated 状态、来源计数、是否用了记忆）关联存储；纳入现有有界诊断分区（同款限制：不含笔记文本与回答内容本身，只存结构与判定）。

**验收**：积累两周数据后可查询"哪类分区组合对应的'有用'率更高"；数据结构与清除入口符合现有隐私披露（README Data and network disclosure 节同步更新）。

## T4【P2·省 token】证据进 context 前先压缩

**问题**：本地证据以段落全文进 context，web 证据带抓取片段——证据多时是最大的分区开销。

**做法**：本地证据降为"标题+要点句（首句+含命中词句）"，全文改为按需（模型可用临时引用再取，ToolGateway 已有 grant 机制可复用）；web 证据只留标题+摘要，页面片段按需 fetch。保留分区预算与 Receipt 标注（`compressed_to_summary`）。

**验收**：中等复杂问题的本地+web 证据分区 token 下降 ≥50%；gold set 中"找原文"类问题仍能通过按需展开拿到全文。

## T5【P2·验证记忆】确认偏好的 on/off 效果对比

**问题**：候选式记忆流程逻辑自洽，但"确认后的偏好真的让回答更好了吗"从未度量——可能确认的几条偏好对体验影响为零，而每轮都占 token。

**做法**：从已确认偏好中选 2-3 条，准备 10 个固定问题，分别在"注入偏好 / 不注入"两态下各答一轮，本人盲评差异（风格是否符合偏好、事实质量是否变化）；结果记录进 docs/evaluation/。同时用 T3 的反馈数据做长期验证（被注入偏好的回答 vs 未注入的"有用"率）。

**验收**：一份含结论的对比报告（偏好有效/无效/需调整注入方式）。若结论是"无效"，考虑把记忆注入也做成按需（T2 的分类器判断是否注入），进一步省 token。

## T6【P3·接通设计】LearningState 落地（按 v1-optimization 文档执行）

**问题**：掌握状态（exposed→questioned→explained→applied + evidenceLevel）设计完成但未实现——记忆体系里最有学习场景特色的部分停在纸面。docs/v1-optimization-toward-v2.md 已明确"差距比想象小，只需接通"，O1-O5 优化点现成。

**做法**：按该文档执行（未解决问题上抛用户确认，不自作主张改设计），重点：用户复述/新情境正确使用才提升 stage、保存 AI 回答不推断掌握、open_question 上交为记忆候选。

**验收**：按 v1-optimization 的验收标准；Receipt 的 learning_state lane 开始出现真实数据。

## T7【可选】诊断面板增加"每分区 token 累计统计"

**做法**：在现有运行诊断里按分区累计输入 token 占比（system/选段/记忆/证据/web/历史），帮助持续定位浪费源。**验收**：面板可见各分区占比曲线。

## 不许动的东西（改动红线）

1. **候选式记忆三关原则**：显式信号 → 3 个不同对话 → 用户确认；确认偏好只控 presentation style 不控事实结论——T5 只验证效果，不改原则。
2. **隐私边界**：搜索只发 query 不发笔记全文；fetch 只开搜索返回或用户给的 URL，私网/凭证 URL 拦截；诊断数据不含用户内容。
3. **Context Receipt 机制本身**（用户可见的上下文透明性）——T2/T4 只改装配策略，Receipt 必须继续完整解释"为什么这个分区没有"。
4. **不做全库向量索引**——只有 T1 的决策规则触发时才对授权 Scope 增量 embedding。
5. 数据有界原则：临时会话/诊断/记忆各分区的数量、时长、字节上限维持。

## 执行顺序建议

T1（先测量，半天-1 天）→ T2（token 根治，1-2 天）→ T3（反馈越早上线越好，数据靠积累，半天）→ T4 → T5 → T6。每完成一项在 docs/evaluation/ 留下前后对比数字——这组数字本身将来就是"个人项目评测化"的完整证据链。
