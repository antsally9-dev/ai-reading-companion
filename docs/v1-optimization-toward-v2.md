# V1 → V2 愿景：小步闭环优化点

> 状态：提案，待评审
> 日期：2026-09-05
> 前置阅读：[product-vision-v2-brief.md](product-vision-v2-brief.md)、[chatgpt-discussion-learning-protocol.md](chatgpt-discussion-learning-protocol.md)、[agent-technical-design.md](agent-technical-design.md)、[agent-development-plan.md](agent-development-plan.md)
>
> 前提判断：V2 愿景（独立 App、学习者模型、图谱层、纠错闭环）一次性做无法形成闭环。本文在 V1（Obsidian 插件 v1.2.1）基础上，以愿景为方向，提出每个都能独立跑通的小步优化点。

## 一、关键发现：差距比简报写的小

精读 V1 实现后发现，`agent-technical-design.md` 里其实已经埋好了 V2 愿景的大部分**纸面设计**，只是没接通：

| 愿景需要 | 简报判断 | 实际状态 |
|---|---|---|
| 学习者模型（已掌握/未掌握） | 缺失 | **半成品**：设计文档 §12 已定义 `MemoryKind` 三分类（偏好/学习状态/纠正）和 `LearningStatePayload`（exposed→questioned→explained→applied 四阶段）；V1 只实现了第一种（explanation_preference） |
| 未掌握藏在提问里 | 缺失 | **半成品**：`QuestionRecord` 已实现且有 status/sourceExcerpt/父子消息链（`conversation-domain.ts:75`），但只活在一个临时会话里，随会话淘汰消失，从未被当作"未掌握信号"聚合 |
| 框架/图谱层 | 缺失 | **有占位**：历史问题检索 lane 已实现（main.ts:3422）；Scope Brief（§8.7.1，确定性清单+可选 AI 摘要）有完整设计但零实现 |
| 纠错闭环 | 缺失 | 真缺失，但"先审后写"的交互模式（web 来源确认保存、摘录草稿编辑）可直接复用 |
| 自学习=了解用户 | 有雏形 | 候选式偏好记忆已上线（`memory-store.ts`），但检测器只认"风格类"正则，且与 ChatGPT 讨论沉淀的教学协议（结构类偏好）不接轨 |

**结论：优化点不是"从零设计新能力"，而是"把设计文档里已有的最小心跳接通"，每步复用 V1 的候选式机制、证据车道、审后写交互。**

## 二、可复用的 V1 资产

- **候选式记忆机制**（`memory-store.ts`）：信号检测 → 相似度去重（≥0.58）→ 3 个不同会话晋级 → 人工审阅（`LearningMemoryReviewModal`）→ 确认才进上下文 → 过期/复核。这套状态机可以直接泛化到非"偏好"类记录。
- **QuestionRecord + 待问清单**：已持久化（session 分区），有"来源片段/提问轮次/回答轮次/父子关系"真实行为数据（backlog 2026-08-17 准备的分支数据）。
- **身份化证据车道 + 历史问题 lane**：personal/user-curated/external/unknown 分 lane，历史问题只带问题不带旧回答。
- **Context Receipt / RunPlan / 工具预算**：任何新 AI 调用都能被约束、可解释。
- **审后写交互**：摘录草稿、web 来源确认保存——纠错功能的产品模式模板。

## 三、优化点（按小 → 大排序）

### O1. 开放问题索引：把"未掌握"从会话垃圾变成学习者模型的第一层

**一句话**：问题暂放/跨会话复现时，聚合为持久的"开放问题候选"，经确认进入长期记忆——这就是愿景里"未掌握的知识藏在提问里"的最小实现。

- **闭环**：提问 → 暂放或已问未解决 → 跨会话再次出现相似问题（复用 similarity ≥0.58 去重）→ 候选"未掌握点" → 审阅弹窗确认（复用现有 Modal）→ 确认后进入上下文（"你在 X 主题还有这些未解决的问题"）→ 新回答主动挂接旧问题 → 用户解决后标记 resolved。
- **复用**：memory-store 状态机、审阅 Modal、QuestionRecord、历史问题 lane。
- **新增**：memory-store 增加 `kind: "open_question"`；会话淘汰时把未解决问题"上交"到全局候选（这是唯一的粘合逻辑）；审阅弹窗按 kind 分区展示。
- **明确不做**：自动判定"已掌握"；向量相似；跨设备同步。
- **设计依据**：技术设计 §8.7 QuestionRecord 本来就有 `status: "open"` 和 `userCorrectionIds` 字段，只是 V1 用的是简化版 status。

### O2. 自查问题（难度闸门）：掌握状态的第一份证据

**一句话**：每个回答可附带一个"自查问题"，用户不看答案用自己的话复述，AI 对照原文与回答只做"是否讲清了"的判定，产生 `learning_state` 候选——这是 ChatGPT 教学协议里"难度闸门"的产品化，也是愿景"已掌握/未掌握"的第二个信号源。

- **闭环**：回答 → 自查问题（可关闭）→ 用户复述 → AI 对照来源证据判定 explained / 未讲清（判定仅限本轮上下文内的证据，Receipt 可见）→ 候选掌握状态 → 确认后影响后续回答的详略（已掌握快速带过、未掌握重讲）。
- **复用**：证据车道（判定材料只有选中原文+本轮回答）、预算控制、候选式确认。
- **新增**：`LearningStatePayload`（设计 §12.5 已定义，四个阶段先只做 `questioned → explained` 两级）；复述输入框与判定调用。
- **明确不做**：打分、间隔重复排期、把"保存过摘录"当掌握证据（设计文档红线）。
- **愿景衔接**：这一步完成后，Memory 才真正同时拥有"偏好 + 掌握状态"两轴，且全部来自用户真实行为，不是模型猜测——这是面试叙事里最硬的部分。

### O3. 纠错闭环：只校对"用户确认要保存的内容"

**一句话**：保存摘录/复述前可选触发"校对"，AI 只对照上下文内的来源找**事实错误、与来源不符、表述含糊**三类问题，每条必须引用原文出处；采纳则改草稿，拒绝则记录 `user_correction` 证据。

- **闭环**：用户独立输出（保存动作）→ 校对（证据只来自本轮上下文，预算受限）→ 逐条采纳/拒绝 → 采纳改草稿后照常走保存流程；拒绝记录为"用户坚持原表述"——这既是纠错记录，也是 O1/O2 的掌握信号。
- **复用**：审后写交互模板、工具预算、Receipt（展示校对用了哪些证据）。
- **新增**：校对 prompt（三分类 + 强制引用出处）；`kind: "user_correction"` 记忆。
- **误纠错防线**（回应简报 kickoff 问题 4）：上下文内没有可靠出处时必须回答"无法校对"，不允许凭模型先验纠错；用户拒绝永不被覆盖；只校对保存内容，不主动批改一切输出。
- **愿景衔接**：补齐"AI 只做回答与纠错"的另一半。

### O4. Scope Brief 确定性清单：用"问题地图"占位"知识图谱"

**一句话**：先实现设计 §8.7.1 里 Scope Brief 的**确定性清单半边**（文件数、主要标题/标签、已确认数、未解决问题列表），回答时给出一行"框架位置"：这个问题属于哪个主题、与你哪些历史问题相邻。

- **闭环**：启用 Scope → 生成确定性清单（无 AI、无全库扫描，沿用现有缓存纪律）→ 回答时检索 lane 命中相关历史问题（已实现）→ 回答头部展示"框架位置"一行 + 相邻问题链接 → 用户解决 O1 的开放问题后地图上的"未解决"计数变化。
- **冷启动答案**（回应简报 kickoff 问题 2）：框架初始 = 文件夹结构 + 标签 + 用户手写的一句 scope 描述，完全确定性，不靠 AI 猜；AI 摘要半边（topicOutline 精化）留到确定性版本被验证有用之后。
- **复用**：knowledge-scope 的 scope 登记与缓存、历史问题 lane、O1 的开放问题。
- **明确不做**：Module/Claim/Relation 全量建模、AI 自动补边、图谱可视化（backlog 已有"最小图谱交互"设计，仍按它说的先验证关系数据有没有用）。
- **chat-archive 合并点**：等 O1+O2+O4 攒出真实的 question/learning-state 关系数据后，再评估用 Registry/Fragment/Claim/Relation 替换 outline label——那时是"用数据驱动合并"，不是现在拍脑袋合并。

### O5. 偏好记忆升级：把教学协议做成"可确认的预置偏好"

**一句话**：把 ChatGPT 讨论沉淀的教学协议（先对象后分类、5–8 节点主流程、难度闸门、连续建模、少章节多细节）整理成一组**预置偏好**，用户逐条确认后生效；同时给检测器补上"结构类"偏好的正则。

- **闭环**：设置页/命令面板提供"采纳教学协议"清单 → 用户逐条确认（沿用候选式哲学：确认才生效、可拒绝、可撤销）→ 确认的条目进入 `getConfirmedPrompt()` 现有通道 → 回答结构改变 → 用户不满意的条目可单独撤掉。
- **复用**：memory-store 全套（检测器 `detectLearningPreferenceSignal` 加 2-3 条结构类正则；`getConfirmedPrompt` 原样）。
- **成本**：全部改动量最小的一项，一天级。
- **愿景衔接**：回应简报 kickoff 问题 5（候选式 vs 更强自动适应）——答案是坚持候选式，但把"已知的好协议"的采纳成本降到一键；这也是 ChatGPT 讨论第 6 条结论（显式 Project Instructions 比隐式推断稳定）在本项目的直接落地。

## 四、建议顺序

```text
第一批（打通"未掌握"信号）：  O5(天级) → O1(周级)
第二批（打通"掌握"信号）：    O2
第三批（补齐"纠错"）：        O3
第四批（给前两批一个"地图"）：O4
```

理由：O1/O5 最小且直接兑现愿景最有辨识度的论断（"未掌握藏在提问里"）；O2 是产品差异化最大的一步，依赖 O1 建立的记忆泛化机制更稳；O4 放最后，因为它消费 O1/O2 产出的数据，先有信号再有地图，避免地图先行的空转。

每批完成标准沿用项目惯例：TS 构建 + lint + 离线确定性测试（候选晋级、确认前不进上下文、校对无出处不发言）+ 桌面/移动手测；新 AI 调用必须有预算与 Receipt。

## 五、本轮明确不做（守住克制）

- 独立 App / 去 Obsidian 化：O1-O4 全部沉淀在 storage adapter 与平台无关模块里（session-store 适配器模式已就绪），迁移路径保留但不启动。
- embedding / 向量库 / 全库索引：继续沿用"性能指标证明必要才立项"的门槛。
- 自动知识图谱、AI 自动补边、自动写 Memory：候选式红线不破。
- 保存即掌握：任何"用户保存过"都不改变学习状态，只有复述/应用/校对中的坚持才产生证据。
