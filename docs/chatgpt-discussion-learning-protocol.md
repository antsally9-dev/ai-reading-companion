# ChatGPT 深度讨论存档：分析 Agent 学习方法

> 来源：https://chatgpt.com/share/6a9be62a-f2bc-83e9-a940-cbe9b9f3b2d9 （标题：分析Agent学习方法）
> 抓取：2026-09-05，经浏览器渲染提取全文。补齐 `product-vision-v2-brief.md` 第一节标注的待补充素材。
> 用途：① v2 产品设计的输入（"回答"侧的用户真实诉求）；② AI PM 面试素材。

## 核心结论摘要

用户上传 3 份学习 Claude Code/Agent 的对话记录，向 ChatGPT 抱怨：**回答很详细，但问题是一个一个回答的，回答之间缺少联系和体系化**，要求总结出今后的回答标准。ChatGPT 的反思凝练为一套"教学协议"：

1. **总原则：降低横向分叉，保留纵向深度**。越到 Runtime/Context/Tool Execution/Protocol/State 这些底层，概念互相依赖，"一个问题拆成四十个知识点"的讲法失效——得到的是一堆标签，不是一个系统。
2. **顺序倒了是最严重的问题**："先给分类，再给实体"（如先讲五套分层，再让学习者反推机器长什么样）。正确顺序：**先建立对象 → 再建立流程 → 再建立关系 → 最后才建立分类 → 最后才进源码细节**。
3. **新对象首次出现必须讲完整**（九件事）：它是什么、谁创建它、从哪来、里面有什么、为什么存在、谁使用它、什么时候产生、什么时候消失、模型能不能看到它。"只介绍名字，不介绍对象"被明令禁止。
4. **主流程图先行**：每章先给一张只有 5~8 个节点的物理主干图（如 tool_use → Parser → Executor → Runtime Tool → ToolResult → Model），地基没干不盖第五层。
5. **从实例长出分类，不从分类反推实例**：用一个真实执行案例贯穿完整数据流，抽象名词都要回到执行轨迹上。
6. **从"问答模式"改为"课程模式"**：AI 负责提前判断前置概念、依赖顺序、每章完成标准；**用户不应承担"自己发现知识缺口再追问"的责任**。
7. **难度闸门**：每章有明确完成标准（"不看答案能自己复述 X"），讲不出来就不叠下一层复杂度。
8. **长回答组织成少数大章节**（4 个抽屉），不是 40 个并列散点。
9. **"连续建模"取代"由浅入深"**：每一步只是把已认识的对象提高一点分辨率（盒子→打开→运行→再拆→挂回总图），而不是每步给一张新图。
10. **Memory/指令落地讨论**：ChatGPT 先误把"仅限项目的记忆"说成"Memory 关闭"后自行纠正；区分了 Project Memory（以前聊过什么）与 Project Instructions（以后怎么协作），并建议把教学协议写入项目指令而非依赖隐式记忆推断——**这本身就是一个"显式偏好固化 vs 隐式自学习"的产品案例**。

## 与 v2 愿景的衔接

- 这份讨论是简报中"**Agent 自学习 = 逐渐了解用户**（回答形式、深度、侧重）"的具体实证：用户真正要的不是更多细节，而是**知识依赖有序、可挂回总框架的课程式回答**。
- "难度闸门"（不看答案能复述）与"未掌握的知识藏在提问里"互为表里：闸门是显式的掌握状态检查，提问是隐式的未掌握信号。
- 第 10 点是现成的面试素材：为什么最终建议写 Project Instructions——候选式/显式固化偏好比从历史对话推断更稳定、可审计。

### 消息2 [assistant]

我觉得你现在指出的问题非常准确，而且它不是"你进入难区以后理解能力跟不上"，而是教学结构已经不适合当前知识难度了。

越到 Runtime、Context、Tool Execution、Protocol、State 这些底层，越不能继续用"一个问题拆成四十个知识点"的方式讲。因为这些概念本身互相依赖：前一个对象连"是什么、从哪来、在哪里、什么时候出现"都没建立起来，后面再告诉你它有语义层分类、协议层分类、生命周期分类，你得到的就会是一堆标签，而不是一个系统。

我现在认为我们真正要改的不是"减少技术深度"，而是：

**降低横向分叉的数量，保留纵向解释的深度。**

这句话可能最能概括你喜欢 Developer / Skill 那两次、但最近越来越吃力的原因。

#### 一、你举的 CLAUDE.md 例子，正好说明现在的回答哪里出了问题

假如我要第一次给你介绍 CLAUDE.md，现在这种讲法可能是：

- CLAUDE.md 属于 Project Context
- 它有 user-level / project-level / local...
- 它属于 Context Source
- 进入某个 Layer
- Compaction 时……
- 和 Rules……
- 和 Memory……

这些话可能都没有错。

但你脑中此时连这个东西本身都还没有形成。

你真正首先需要知道的其实应该是这种东西：

```
Claude Code
│
│ 启动 / 进入项目
│
▼
在磁盘里发现 CLAUDE.md
│
│ 谁负责找？
▼
Claude Code Harness
│
│ 读取里面的文字
▼
把这些文字变成本 Session 的项目指导信息
│
│ Context Builder 在需要的时候组织它
▼
送进 Claude 当前看到的 Context
│
▼
Claude 在后续读代码、修改代码时参考这些规则
```

先把这条真实的数据流建立起来。

然后才开始问：

- 它到底能放在哪几个位置？
- 为什么存在这些位置？
- 这些位置按照什么标准分类？
- 根目录的和用户级的是不是一样？
- 子目录的为什么能覆盖？
- 什么时候加载？
- 每轮重新读吗？
- 什么时候失效？
- Compaction 后怎么办？
- Subagent 会继承吗？

也就是说，对一个新对象，先把"这个东西活在系统里的一生"讲出来，然后才有资格分类。

你刚才说的：

来源是什么、分类标准是什么、各自起什么作用、怎么加载、怎么应用

我认为以后应该成为强制要求，而不能指望你发现缺口以后再来追问。

#### 二、最近真正的问题是"先给分类，再给实体"

这是我现在反思下来最严重的问题。

你刚刚说：一上来开始讲不同语义层分类、协议层分类……

这里其实顺序倒了。

比如一个刚接触汽车的人，我如果上来告诉他：机械层、电气层、控制层、信息层、安全层，然后说：刹车既属于机械执行层，又属于控制语义层，在 CAN 协议里又是……

理论上很严谨。

但这个人连：发动机在哪里、刹车是什么、方向盘怎么连接车轮，都还没建立起来。

这时候"多维分类"只会增加认知负担。

我们最近研究 Agent 也出现了这个问题：

- Protocol Role
- Context Layer
- Runtime State
- Session State
- Semantic Layer
- API Layer
- ToolUseContext
- Current Mode
- Permission Mode
- ...

每一个词都可以成立，但没有先形成一台能运行起来的 Agent 机器。

所以今后顺序应该改成：

```
先看机器
↓
再看机器里的零件
↓
再看零件怎么运动
↓
最后才用不同坐标系分析这台机器
```

而不是：

```
先给你五套坐标系
↓
然后让你自己推断机器长什么样
```

#### 三、为什么 Developer 那次虽然也很长，你反而比较容易接受

我现在重新看这个差异，觉得原因不是 Developer 比 Tool Runtime 简单。

而是 Developer 那次大量使用了这种方式：

"你现在混淆的是三个不同维度。"

然后马上给你一个实体关系：

```
Harness / Runtime
       │
       │ 创建
       ▼
LLM Request
       │
       ├── Developer Message
       ├── User Message
       └── ...
       ↓
      Model
```

于是 Developer 有"家"了。

之后才继续拆：Developer ≠ AGENTS.md、Developer ≠ Runtime、Developer ≠ config.toml。

所以即使继续讲很多东西，你脑子里始终有一个锚：Developer 就是 Request / Context 里的某种东西。

技能与上下文管理也是类似的。你最开始问的是："Skill 正文如果被压缩怎么办？"

回答逐渐建立出了：

```
Skill 文件
↓
Skill Registry
↓
Skill catalog
↓
选中 Skill
↓
SKILL.md body
↓
Model Context
↓
Compaction
↓
Rehydration
```

所以内容很长，但它实际上是在顺着一个对象的生命周期纵向钻。

而最近一些回答变成了：A 是什么、B 是什么、C 分几种、D 和 E 区别、F 又有三层、G 源码函数、H 协议结构……

这叫横向展开。

**四十个标题不是问题。四十个同时需要新建脑内对象的标题才是问题。**

#### 四、以后我们的学习方式应该从"问答模式"改成"课程模式"

这是我觉得最重要的改变。

以前事实上是：你不懂 A → 问 A → 我补 A；又遇到 B → 问 B → 我补 B；发现 A 和 B 连不上 → 再问关系。

这非常消耗你。

而且越到底层越严重，因为你甚至不知道"自己缺的是哪一个前置知识"，自然也不知道该问什么。

以后应该反过来。

我在开始一个新的复杂模块时，要负责提前判断：

- 理解这个模块需要哪些前置概念？
- 哪些东西现在必须讲？哪些现在不要讲？
- 这些概念应该按什么依赖顺序出现？
- 讲完 A 以后，你需要理解到什么程度，才能进入 B？

也就是把回答当成课程章节设计，而不是 FAQ。

#### 五、我认为以后复杂技术内容应该固定遵守下面这套顺序

1. **先告诉你"这一章到底在研究什么"**。不先抛术语，而是用一句非常具体的话限定范围。例如研究 Tool Runtime 时先说："我们这一章只研究：模型已经生成一个 tool_use 以后，Claude Code 到底怎样把它变成一次真实工具执行，再把结果送回模型。"

2. **先画一张只有 5～8 个节点的物理主干图**。例如：

```
Model
  ↓ tool_use
Streaming Parser
  ↓
Tool Executor
  ↓
Runtime Tool
  ↓
ToolResult
  ↓
Model
```

这一阶段禁止一下加入 Hook、Permission、Scheduler、MCP retry、schema preprocessing 等十几个旁枝。

3. **第一次出现一个重要对象时，必须把它讲完整**。固定回答：它是什么；谁创建它；它从哪来；里面具体有什么；为什么要有它；谁使用它；什么时候产生；什么时候消失；模型能不能看到它。比如 ToolUseContext 没讲完这九件事之前，就不应该把五个依赖它的新函数继续往下堆。

4. **随后跑一次完整实例**。例如 Claude 输出 Read("src/a.ts")，我们真的一路追：这个 tool use 长什么样 → Parser 得到什么 → Executor 收到什么 → validation 检查什么 → permission 为什么在这里 → tool.call() 得到哪些参数 → 最终 ToolResult 长什么样 → 下一次请求怎么使用它。所有抽象名词都必须回到这条执行轨迹上。

5. **只有主流程真正成立以后，才讲分类和旁枝**。例如这时候再说："我们刚刚看到的是 Runtime 数据流。现在为了读源码，需要再区分 Protocol Role 与 Context Layer。"这样你知道分类是在分析刚才已经认识的东西，而不是突然出现了一套新世界。

6. **最后才进入源码函数和特殊机制**。runToolUse()、processQueue()、Hook、reader/writer lock、retry 都应该成为主流程上某一个节点的"放大镜"，而不是并排出现的几十个知识点。

这其实就是我要采用的新教学协议。

#### 六、还有一个非常重要的规则：以后不允许"只介绍名字，不介绍对象"

你这次说 CLAUDE.md 的问题，我特别认同。

以后如果我写：

- Claude Code 有：CLAUDE.md、Rules、Memory、Skills……

这只能算目录，不能算讲解。

真正讲 CLAUDE.md，至少应该完成：

```
CLAUDE.md
│
├─ 它为什么存在？
├─ 它是谁创建/维护的？
├─ Claude Code 去哪里发现它？
├─ 为什么会有不同 scope？
├─ scope 的分类标准到底是什么？
├─ 多份 CLAUDE.md 同时存在怎么办？
├─ Session 开始时什么时候加载？
├─ 进入 Context 的具体内容是什么？
├─ 每个 Turn / Request 是否重复加载？
├─ 修改文件以后怎样刷新？
├─ Compaction 后怎样处理？
├─ Subagent 是否拿得到？
└─ 它和 Rules / Memory / Skill 到底哪里不同？
```

而且不能十四个问题分别一句话回答。

应该先用一个真实项目：

```
~/
└── CLAUDE.md

repo/
├── CLAUDE.md
└── frontend/
    └── CLAUDE.md
```

然后让你看到 Claude Code 在 repo/frontend 工作时到底发生什么。

**从实例长出分类，而不是从分类反推实例。**

#### 七、我们还需要一个"难度闸门"

这是过去几轮没有做好的地方。

当一个回答里已经出现：Protocol Role、Context Layer、Session Runtime State、ToolUseContext——如果其中 ToolUseContext 你都没有真正理解，我还继续引入：contextModifier、concurrency safe、exclusive scheduler、Input Schema preprocessing、Hook pipeline……

这在教学上就是错误的。

以后每个大章节应该有一个非常明确的完成标准。

例如：这一节结束以后，你应该能够不看答案，自己解释："模型生成 tool_use 后，到 tool.call(input, context) 之间发生了什么。"

只要这句话还不能顺畅讲出来，我们就不继续叠下一层复杂度。

不是让你每一段都考试。而是由我控制知识依赖，不再出现：前面的地基还没干，已经盖到第五层。

#### 八、长回答本身不是问题，但要从"四十个点"变成"四个章节"

你说最近可能一次四十几点。

我觉得以后可以仍然很长，但是结构应该更像一本教材：

```
第 1 章：先认识这个组件   └─ 很详细
第 2 章：看它怎样工作     └─ 很详细
第 3 章：把它放进整个 Agent └─ 很详细
第 4 章：再进入真实实现   └─ 很详细
```

而不是 1. 2. 3. 4. 5. …… 39. 40. 的并列。

前一种虽然可能同样有一万字，但你的脑中只有四个"抽屉"。

后一种需要同时管理四十个抽屉。

这两种阅读负担差别非常大。

#### 九、所以我们真正追求的不是"由浅入深"，而是"连续建模"

"由浅入深"这个词其实还不够。因为很多回答看起来也是先简单介绍再深入，但简单介绍可能只是："X 有三层，分别是 A/B/C。"这并没有帮助你形成模型。

我以后更应该做的是：

- 第一步：你脑中只有一个盒子。
- 第二步：把这个盒子打开，看里面两个主要部件。
- 第三步：让两个部件真的运行一次。
- 第四步：发现其中一个部件其实还可以继续拆。
- 第五步：再把它拆开。
- 第六步：回头看看拆开的东西仍然属于最开始哪个盒子。

这叫连续建模。

**每一步只是把你已经认识的东西提高一点分辨率。而不是每一步都给你一张新的图。**

这可能才是你现在最需要的学习方式。

我觉得我们现在已经可以把标准定得非常明确了：技术深度不降；细节甚至可以继续保持 Developer 和技能与上下文管理那两次的密度。真正要改变的是：先建立对象，再建立流程，再建立关系，最后才建立分类；一个章节沿一条主线纵向钻到底，不同时横向展开十几个新概念。

而且你不应该再承担"哪里没讲我自己发现、然后再追问"的责任。进入一个新模块以后，来源、结构、作用、加载、应用、生命周期、与相邻组件关系这些本来就应该由我主动补齐。

我建议我们接下来回到你刚才那个已经让你比较吃力的 Claude Code 对话时，不继续接着原来的四十多个点往下走，而是把正在学习的那一块重新组织成一章，从最上面的"这台机器到底在干什么"重新搭起来；已经懂的地方会快速经过，真正没建立起来的地方再纵向讲透。

#### 1. 你现在这种设置是什么意思

如果这个项目设置的是仅限项目的记忆，那么大致是：

```
                    当前这个 Agent 项目
                           │
          ┌────────────────┴───────────────┐
          │                                │
     本项目对话                        本项目文件
          │                                │
          └───────────可以互相参考──────────┘

                           X
                           │
             项目外的普通聊天 / 其他项目
```

也就是说：

- 当前项目里的对话可以参考同一个项目里的其他对话；
- 可以使用这个项目中的文件和上下文；
- 不会引用项目外的聊天和记忆；
- 项目里的信息也不会被外面的聊天引用。

所以这其实正适合我们现在的 Agent 学习：ai agent 项目形成一个相对独立的长期学习空间。

这也解释了为什么我刚才能够看到项目里此前关于 Tool Runtime、Context、Skill 等对话的部分共享上下文。

不过还有一个容易混淆的地方：**Project Memory ≠ 一张"Saved Memory 清单"**。官方目前明确说，项目记忆没有一个像个人 Saved Memories 那样可以查看的"项目记忆列表"。它更多是让 ChatGPT 在回答时利用同项目的历史对话。

所以你刚才说"把这条标准记录到我们的 memory"，从产品机制上，更准确地应该拆成两个需求：

- A. 希望以后能参考我们今天这段讨论 → Project-only memory / 项目聊天历史可以帮助做到
- B. 希望这成为一个非常稳定、明确的回答规则 → Project Instructions 更合适

对于我们今天定下来的教学标准，我更建议放到 Project Instructions，而不是只依赖项目记忆。

#### 2. Project Instructions 是什么

它可以理解成：只对这个项目持续生效的一份显式说明书。

官方说明，Project Instructions 只作用于当前项目，而且会覆盖你的全局 Custom Instructions。

所以非常适合写："在 ai agent 项目中，我希望你怎样给我讲 Agent。"

这就比"希望系统从过去几十轮里自己总结出我的偏好"稳定得多。

可以把两者理解成：

- Project Memory = "我们以前聊过什么"
- Project Instructions = "以后在这个项目里应该怎样和我协作"

对我们现在这个需求，后者尤其重要。

#### 3. 怎么添加 Project Instructions

目前官方步骤是：打开这个项目 → 右上角 ... → Project settings / 项目设置 → 找到 Project Instructions / 项目指令 → 填入内容 → 保存。

你在同一个 Project settings 里面应该也能看到 Memory：Default memory / Project-only memory。

官方从 2026 年 8 月起已经支持在已有项目中修改这项设置。

本项目用于系统学习 Agent、Coding Agent、Harness、Claude Code、Codex 等相关架构与实现机制。

在回答技术学习问题时，请遵循以下教学原则：

1. 保持较高技术深度和细节密度。不要为了"易懂"而过度简化。回答风格应接近此前"Developer 角色说明"和"技能与上下文管理"中的详细程度：重视概念边界、数据流、生命周期、具体例子、真实实现以及必要的源码细节。

2. 但不要把回答组织成大量彼此并列、缺乏主线的知识点。降低横向分叉，保持纵向深入。复杂回答应该像一章课程，而不是 FAQ 或几十个散点。

3. 学习一个新对象时，先建立"对象本身"，再讲分类。对于 CLAUDE.md、ToolUseContext、Skill、Runtime State 等重要概念，应主动讲清：它是什么；为什么存在；来源是什么；谁创建、发现或维护；内部具体包含什么；在整个 Agent/Harness 架构中的位置；模型是否能直接看到；如何加载；如何进入模型 Context；如何被使用；什么时候刷新、失效或重新加载；Session / Turn / Request / Compaction 等生命周期中如何变化；与相邻概念有什么区别和联系。

4. 对复杂模块，先给出一张只有约 5～8 个核心节点的主流程图，让我先知道"这台机器怎样运行"，然后再逐个放大节点。不要在主流程尚未建立时，同时引入大量语义层、协议层、Runtime 层等分类。

5. 优先按照"对象 → 流程 → 关系 → 分类 → 实现细节"的顺序讲解，而不是"先给多套分类 → 再让我反推实际系统"。

6. 使用连续建模方式：先建立一个粗粒度模型；再打开其中一个节点；跑一次完整过程；再提高这一部分的分辨率；最后把新知识重新挂回原来的总图。尽量不要每解释一个问题就重新创建一套新的架构图或概念体系。

7. 对流程性问题，尽量使用一个贯穿始终的真实案例，沿完整数据流解释。例如从模型产生 tool_use，一直追踪到 Parser、Tool Executor、Runtime Tool、ToolResult，再回到下一次 Model Request，而不是分别孤立解释每个组件。

8. 在引入新术语前检查前置概念。如果当前关键对象尚未建立清楚，不要继续叠加更多高级术语。技术深度可以很高，但知识依赖必须按顺序建立。

9. 回答长短不是主要限制。可以长篇详细，但应组织成少量大章节，每章围绕一个明确问题深入，而不是出现几十个同等级标题和知识点。

10. 始终把当前问题放回一个稳定的 Agent 总框架中，至少区分：Harness / Runtime 软件架构；一次 LLM Request / Model Context 的结构；Session / Turn / Request / Compaction 等状态与生命周期；模型自身的 Planning、Tool Use、Reasoning 等能力。不要把这些不同维度混在同一级结构中。

11. 对 Codex、Claude Code 等具体产品，先解释通用机制，再进入产品实现。明确区分：通用 Agent/Harness 原理；官方文档明确确认的机制；源码能够确认的当前实现；基于现象或架构做出的合理推断。不要把某个产品的当前实现误讲成通用原理。

12. 不要依赖我自己发现知识缺口之后再追问。对于理解当前主题必要的来源、结构、作用、加载、应用和生命周期等前置信息，应主动补齐。

核心目标：保持技术深度，但让所有细节逐步累积成一个连续、可复述的 Agent 系统模型，而不是形成大量彼此孤立的知识块。
